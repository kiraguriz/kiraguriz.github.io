01 / THE PROBLEM

A card game becomes a state problem over a network.

The application supports up to eight client connections. Each player has a connection and a game state, while the server owns authoritative game decisions. The challenge is keeping network handling and interface behavior from leaking into the rules.

What I owned

I built the networked client and server, separated hand evaluation from the interface, and implemented the betting and payout rules as testable logic.

BUILT WITHJava / JavaFX / TCP sockets / JUnit

02 / KEY DECISIONS

The choices
behind the work.

Implementation is a series of decisions. These are the ones that shape this project.

01

Let the server decide the outcome.

Clients render state and send player actions. The server owns dealing and outcomes, with serialized objects carrying game state over TCP.

THE TRADEOFFThe transport and both sides of the application need compatible object definitions.

02

Give each connection a handler.

The server accepts connections and assigns a handler thread to each client, maintaining a synchronized client list.

THE TRADEOFFThis keeps connection handling separate, while introducing shared-state and lifecycle concerns.

03

Test rules without launching the interface.

Hand evaluation, dealer qualification, and payout calculations are separated from JavaFX controllers. Seventeen JUnit tests cover hand rankings and payouts, including edge cases.

THE TRADEOFFTests establish the cases they cover; concurrency and disconnection behavior need their own runtime checks.
