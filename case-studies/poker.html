01 / Problem

A card game is really a state machine.

Three Card Poker is simple to play and surprisingly fussy to build correctly: ante and play bets, an optional Pair Plus side bet, a dealer who only qualifies on Queen-high, and payouts that depend on exact hand ranking.

Putting it on a network adds the real difficulty — many players, one authoritative deck, and a server that has to keep every connection's state straight without letting one slow client stall the rest.

02 / Approach

Three rules I held to.

① Server owns the truth

The deck, deal, and outcome live on the server. Clients render state and send intent; they never decide who won.

② One thread per player

Each client runs on its own handler thread off a shared, synchronized list so a slow connection can't block the table.

③ Logic apart from UI

Hand evaluation is pure, static, and unit-tested — kept out of the FXML controllers so the rules can be proven, not eyeballed.

04 / What I built server · client · game logic · tests

The actual work.

Server
A multi-threaded TCP server accepting up to eight clients, each on its own handler thread off a synchronized client list.
Transport
Java object serialization over sockets to move deals, bets, and results between server and clients as typed game objects.
Logic
Pure hand evaluation — ranking, dealer qualification, high-card tiebreaks, Pair Plus payouts, and the A-2-3 straight edge case.
Client
JavaFX MVC with FXML scenes and custom CSS for the welcome, table, and win/lose flows, kept separate from the rules.

Concurrency and clean boundaries.
