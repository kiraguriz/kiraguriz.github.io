01 / THE PROBLEM

Aircraft move. Connections drop. Data gets old.

A map is only useful when its state is understandable. A plane spotter needs to find an aircraft, inspect its details, and know whether the information is still fresh. I treated loading, missing data, and refresh behavior as part of that same workflow.

What I owned

I built the client, API, and shared type package. My focus was the handoff between changing aircraft data and a usable phone interface.

BUILT WITHReact Native / Expo / TypeScript / Fastify / SQLite

02 / KEY DECISIONS

The choices
behind the work.

Implementation is a series of decisions. These are the ones that shape this project.

01

Keep the provider behind an API.

The client uses an application-owned contract rather than depending directly on a flight-data provider. A Fastify service handles polling and cached responses; shared TypeScript types keep the client and server aligned.

THE TRADEOFFThe benefit is a smaller client contract. The cost is owning cache behavior, freshness, and backend operations.

02

Let the map lead, then add detail.

Aircraft markers establish the spatial context. Selecting an aircraft brings its callsign, heading, altitude, and other available details into a supporting sheet.

THE TRADEOFFThe detail view needs to stay useful when optional fields are missing.

03

Make verification specific.

The project includes lint, type checks, builds, and Jest checks. The screenshots here show an archived iOS interface capture, with the capture date stated alongside them.

THE TRADEOFFA screenshot demonstrates an interface state; it does not establish current provider availability or an app-store release.
