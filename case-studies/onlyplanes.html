01 / Problem

Plane spotting needs more than a map.

Plane spotting needs a mobile-first workflow that joins live aircraft positions, searchable flight details, spotting places, and lightweight community context.

The hard part is not drawing a marker. The hard part is making changing aircraft data feel trustworthy enough for someone standing outside with a phone.

02 / Approach

Three rules I held to.

① Map first

The tracker starts from aircraft context, with lists and details supporting the map instead of replacing it.

② Thin backend

A Fastify service polls OpenSky into an in-memory cache (SQLite + WAL behind it) so the phone never talks to the raw stream.

③ Trust the state

Routes, markers, fallbacks, and refresh behavior are treated as product details, not plumbing.

04 / What I built mobile · api · release review

The actual work.

Monorepo
A TypeScript monorepo spanning a React Native/Expo client, a Fastify backend, and a shared type package so contracts stay in sync.
Backend
Fastify + SQLite (WAL) polling OpenSky into an in-memory cache, serving REST endpoints for bounding-box queries, flight detail, and callsign/ICAO24 search.
Map
An interactive live map (MapKit on iOS, Google Maps on Android) with directional markers and smooth interpolation between ~5s updates.
Release
Health endpoint, production config, fallback states, and GitHub Actions CI/CD running lint, typecheck, build, and Jest on every push.
