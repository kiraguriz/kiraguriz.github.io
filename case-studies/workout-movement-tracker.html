01 / THE PROBLEM

A useful coach needs more than the last message.

Meals, workouts, body metrics, goals, and previous suggestions become less useful when they live in disconnected flows. The central engineering problem was keeping that context structured and persistent, then passing the right information into coaching features.

What I owned

I led a four-person team building a Flutter workout and nutrition tracker with ML Kit pose detection and HealthKit/Health Connect integration. I owned the SQLite repositories and versioned schema migrations, built the USDA food search, integrated AI coaching flows, and connected nutrition and goal features to stored user context.

BUILT WITHFlutter / Dart / SQLite / Gemini / ML Kit

02 / KEY DECISIONS

The choices
behind the work.

Implementation is a series of decisions. These are the ones that shape this project.

01

Make local records the foundation.

SQLite repositories hold meals, workouts, body metrics, goals, and saved AI results. Features read from explicit data domains instead of relying on a temporary conversation.

THE TRADEOFFSchema changes and migrations become product work, because saved context has to remain readable.

02

Put AI inside an existing workflow.

Gemini supports tips, workout suggestions, diet advice, feedback, and goal adjustments. Responses are cached by an input fingerprint, so unchanged meals skip a repeat API call, and saved outputs can be revisited alongside the records that informed them.

THE TRADEOFFPersisting an output helps continuity; it does not make the recommendation medically validated.

03

Keep nutrition lookup responsive.

Search against USDA FoodData Central waits 500 ms after the last keystroke, discards responses that arrive after a newer query, and stores results in SQLite so recently used foods load locally.

THE TRADEOFFCaching reduces repeated lookups, but the interface still needs to distinguish unavailable data from an empty result.
