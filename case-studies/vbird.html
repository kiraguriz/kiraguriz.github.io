01 / THE PROBLEM

The learning loop is only as good as its data.

Comparing two bird photos is a simple interaction. Preparing a trustworthy pair is more involved: species labels, images, facts, and source records have to agree. That preparation belongs upstream of the user’s next swipe.

What I owned

I built the app and its data system: casual comparisons, an FSRS-based review mode, a Supabase backend, and an offline pipeline that prepares species content before it reaches the interface.

BUILT WITHExpo / TypeScript / Supabase / Python

02 / KEY DECISIONS

The choices
behind the work.

Implementation is a series of decisions. These are the ones that shape this project.

01

Offer two rhythms of practice.

Casual mode supports quick same-species comparisons. The learning mode uses FSRS to schedule review, so returning users have a different path from a quick first visit.

THE TRADEOFFThe modes share content, but need distinct expectations about pacing and progress.

02

Prepare content before runtime.

An offline Python pipeline gathers and shapes material from eBird, Wikidata, Wikipedia, and iNaturalist. Gemini assists extraction; it is a processing tool rather than an original factual source.

THE TRADEOFFOffline preparation makes validation possible before content reaches the app, at the cost of maintaining a separate pipeline.

03

Keep learning state with explicit ownership.

Supabase provides the database, authentication, storage, and functions. Row-level security and migrations are part of the schema design.

THE TRADEOFFAccess rules and schema changes must evolve together; naming RLS alone does not prove every policy is correct.
